# Cassandra Persistence Backend for Helios

Alan Cruz, Anastasia Bryzgalova, Diya Subhashbhai Patel, Sara Lahourpour, Samuel Michaels Rodriguez · Draft, October 2026

## Summary

We propose adding an Apache Cassandra backend to `helios-persistence`, scoped to the capabilities the [Backend Capability Matrix](https://github.com/aacruzgon/hfs-CS4411/blob/a5e74a3604b181722a2d02b11f29cc76e91520bd/crates/persistence/README.md#backend-capability-matrix) marks as planned (○) for Cassandra, minus bulk export, bulk-submit ingest and the `:exact` modifier. That means create, read, update and delete (CRUD), version-specific read (vread), optimistic locking, batch bundles, token, date and URI search, and cursor pagination.

The backend must fit the architecture laid out in [Building a Modern FHIR Persistence Layer (discussion #28)](https://github.com/HeliosSoftware/hfs/discussions/28). Concretely, we will implement the focused storage traits rather than a new interface, scope every operation by `TenantContext`, report only what we actually support, and reject the rest explicitly.

With that scope and architecture in mind, this document is written for maintainers and the team. We would like feedback on four things: the trait surface we plan to implement, the Cassandra data model, the consistency strategy between resource rows and index rows, and the decisions we have taken where the code, the matrix or the spec left a choice open. Each of those is marked **Decision** in the section it belongs to.

This is the design discussion behind our CS 4411 project proposal. The baseline revision we refer to throughout is `a5e74a3604b181722a2d02b11f29cc76e91520bd`, which exists in our fork and upstream.

## Background: the architecture we must respect

The Cassandra backend adds a storage technology, not a new architecture, and that architecture is set out in [Discussion #28](https://github.com/HeliosSoftware/hfs/discussions/28). Helios sits in the "extensible interface layer + polyglot persistence" quadrant: a trait-based layer that any storage technology can implement, with a unified FHIR API above it.

In #28, Cassandra is named as a fit for "web-scale data requirements without breaking the bank". The principles below come from #28, and each one constrains our implementation.

| Principle in #28 | What it means for Cassandra |
| --- | --- |
| Decompose the FHIR spec into focused traits. `ResourceStorage` "knows nothing about search, nothing about REST semantics, nothing about transactions." | Implement `ResourceStorage`, `VersionedStorage` and `SearchProvider` separately. A capability we do not support means we do not implement its trait, or we refuse it explicitly. No catch-all Cassandra interface. |
| Capabilities extend the base by trait inheritance (`VersionedStorage: ResourceStorage`; history builds on versioning). | vread goes in `VersionedStorage`. The REST layer checks `If-Match` itself and uses `ResourceStorage::update` as the compare-and-swap. History is not planned, but the server's trait bound requires the history traits, so they exist only as stubs that refuse. |
| Multitenancy is not optional. Every operation takes a `TenantContext`; there is no escape hatch. "The tenant_id must be the leading column in composite indexes." | The tenant is part of every partition key, so a query without a tenant cannot be written. |
| Search is a base trait plus extension traits (chained, terminology, text). | Implement base `SearchProvider` only. The include and revinclude providers are compile-only stubs. No chaining, `_include`, terminology or text search. |
| Transactions only where atomic all-or-nothing semantics exist. Batch entries are independent. | No `TransactionProvider`. Batch works because the REST layer runs each entry against `ResourceStorage`. |
| Backends declare capabilities, and queries are validated at runtime: capability checking "fails fast with clear error messages". | Declare exactly token, date, URI and cursor paging. The REST layer validates modifiers against parameter types itself, but never calls the shared `validate_search_query`, so our search path refuses unsupported parameters and modifiers as well. |
| Composite storage routes operations to specialized backends (primary, search, graph, terminology). | Cassandra must work as a standalone primary. It also must not block a later "Cassandra + Elasticsearch" composite, which the README lists as planned. |
| Security first: database access must not bypass FHIR authorization. Audit goes to a separate store. | Authorization and audit stay above the backend. Cassandra never stores AuditEvents of its own. |

Two cautions about reading #28 today:

- **Its feature matrix is an early, work-in-progress example.** It shows Cassandra with keyspace-based multitenancy, `:exact` ✓, `:missing` "Limited" and history "Limited". The persistence README matrix supersedes it and "reflects the actual implementation status", so we follow the README.
- **Its code is illustrative.** The real signatures have moved on. For example, `create` now takes `resource_type`, a `Value` and a `FhirVersion`, and search returns `SearchResult`. We implement against the code at the baseline revision, listed in the traits section below.

## Scope: the Cassandra column of the capability matrix

With those constraints in place, we implement every capability marked ○ (planned) for Cassandra except bulk export, bulk-submit ingest and `:exact`, and nothing marked ✗. The matrix is in the persistence README under [Backend Capability Matrix](https://github.com/aacruzgon/hfs-CS4411/blob/a5e74a3604b181722a2d02b11f29cc76e91520bd/crates/persistence/README.md#backend-capability-matrix). We checked the Cassandra column cell by cell: it is identical at the baseline revision and at today's HEAD.

| Matrix row | Cassandra cell | Our plan |
| --- | --- | --- |
| CRUD | ○ | In scope |
| Versioning (vread) | ○ | In scope |
| Optimistic locking | ○ | In scope: `If-Match` mismatch is 412 at the REST layer; a lost concurrent-write race is 409 from our compare-and-swap |
| Batch bundles | ○ | In scope (REST layer, needs `ResourceStorage` only) |
| Token search | ○ | In scope, including `_id` |
| Date search | ○ | In scope, including `_lastUpdated` |
| URI search | ○ | In scope |
| `:exact` modifier | ○ | Not implementable: FHIR defines it for string only, and string search is ✗. The REST layer already returns 400 for `:exact` on any other type; we repeat the check. The cell should become ✗ with a note, not ✓. |
| Cursor (keyset) pagination | ○ | In scope |
| Bulk export | ○ | Out of scope for this project |
| Bulk submit ingest | ○ | Out of scope for this project |
| Instance, type and system history; delete history | ✗ | Not implemented |
| Transaction bundles, conditional operations, conditional patch | ✗ | Not implemented |
| Per-user settings | ✗ | Not implemented |
| String, reference, number, quantity, composite search | ✗ | Rejected with 400 |
| `:contains`, `:text`, `:not`, `:missing`, `:above`/`:below`, `:in`/`:not-in`, `:of-type`, `:text-advanced` | ✗ | Rejected with 400 |
| `_text`, `_content`, `_filter`, chaining, `_has`, `_include`, `_revinclude` | ✗ | Rejected (see the rejection section for how each actually fails) |
| Offset pagination; single- and multi-field sorting | ✗ | Not supported; results follow one fixed order |
| Bulk submit REST worker | ✗ | Not implemented |
| Multitenancy rows | — (no backend in tree) | Shared schema with the tenant in every key, matching the other backends |

Two parameters need a note because they are not matrix rows: `_id` and `_lastUpdated`. The REST layer sends them to `search()` on its own, and chain, `_list` and include resolution are rewritten into `_id` filters before the backend is called. Both are cheap for us (`_id` is a point read on `resources`; `_lastUpdated` is a slice on `resources_by_type`), so they are in scope.

One more scoping note: we test against FHIR R4 only, but nothing in the backend is tied to R4. Helios decides the FHIR version per request and stores it on every resource, and the backend follows that mechanism so that R4B, R5 and R6 need no backend changes later. The FHIR versions section below spells this out.

Once the backend exists, the README's statement that it "reflects the actual implementation status" means the Cassandra column must change. Specifically, ○ becomes ✓ for what ships, `:exact` becomes ✗ with a note, the multitenancy rows are filled in, and the note below the table that says Cassandra has no backend is removed. The same "no Cassandra backend" statement appears in `src/backends/mod.rs`, `src/lib.rs`, `src/composite/mod.rs`, the placement table and backend list further down the README, `ROADMAP.md`, the changelog, and a hard-coded Cassandra table in `tests/common/capabilities.rs` that already disagrees with the README.

## What the FHIR specification requires

We implement and test against FHIR R4. The matrix links point to [build.fhir.org](https://build.fhir.org), the current development build. The two agree on most in-scope rules, but not all; the table marks the rows where they differ, and the list after it collects the differences that affect our tests. The REST layer formats HTTP, so the backend's job is to supply the data and the errors that make these rules hold.

| Capability | Spec | Rules the backend must make true |
| --- | --- | --- |
| CRUD | [R4 http.html#create](https://hl7.org/fhir/R4/http.html#create), [build](https://build.fhir.org/http.html#create) | On create the server assigns `id`, `meta.versionId` and `meta.lastUpdated` and SHALL ignore client values; on update the client `id` must match the URL. Delete of an already-deleted or unknown id has no effect and returns 200/204. For servers that keep history, a delete is recorded as a history entry with no content. A read after delete returns 410 Gone (R4 states it as fact; the build says "when the server wishes to indicate that the resource is deleted"), and an unknown id returns 404. A later PUT may bring a deleted resource back. |
| vread | [R4 http.html#vread](https://hl7.org/fhir/R4/http.html#vread) | `GET [type]/[id]/_history/[vid]` returns that version. A deleted version "should return a 410". |
| Optimistic locking | [R4 http.html#concurrency](https://hl7.org/fhir/R4/http.html#concurrency) | The ETag is the weak version id, `W/"vid"`. An `If-Match` mismatch returns 412 and changes nothing. A 409 is permitted for other conflicts; a server that requires `If-Match` returns 400 when it is absent. Mapping a lost concurrent-write race to 409 is Helios's choice, not the spec's. |
| Batch | [R4 http.html#transaction](https://hl7.org/fhir/R4/http.html#transaction) | Entries SHALL have no interdependencies that change the server, and one failure SHOULD NOT alter another. The batch returns 200 with a status per entry. The build adds that two entries updating or deleting the same resource count as an interdependency. |
| Token | [R4 search.html#token](https://hl7.org/fhir/R4/search.html#token) | Four forms: `code` (any system), `system\|code`, `\|code` (no system property) and `system\|`. Values come from Coding, CodeableConcept (any coding), Identifier (system + value), ContactPoint, code, boolean, uri and string; the build adds id. Matching is literal (no subsumption) and case-sensitive unless the context says otherwise; `_id` is always case-sensitive; only when it is ambiguous SHOULD servers match case-insensitively. For ContactPoint, uri and boolean elements the pipe form SHALL NOT be used. |
| Date | [R4 search.html#date](https://hl7.org/fhir/R4/search.html#date) | Every value is a range. A partial date covers its whole year, month or day. A Period may be open-ended, and a Timing spans its earliest to latest event. The prefixes `eq ne gt lt ge le sa eb ap` compare ranges, and `eq` is the default. R4 defines the prefixes by range overlap; the build restates them as boundary tests (differs, see below). |
| URI | [R4 search.html#uri](https://hl7.org/fhir/R4/search.html#uri) | Exact whole-URI matching, case- and accent-sensitive (R4 adds escape-sensitive; the build drops that word). No normalization of trailing slashes or `urn:oid` values is specified. |
| Modifiers | [R4 search.html#modifiers](https://hl7.org/fhir/R4/search.html#modifiers), [build](https://build.fhir.org/search.html#modifiers) | `:exact` is defined for string parameters only (R4: "For string: :exact returns results that match the entire supplied parameter"; the build says it outright: "exact is only allowed on string type search parameters"). Both versions: a server **SHALL** reject a search with an unsupported modifier; the spec's example is 400 with an OperationOutcome. |
| Combining parameters | [R4 search.html#combining](https://hl7.org/fhir/R4/search.html#combining) | Different parameters, or a repeated one, are ANDed. Comma-separated values are ORed. A modifier on an OR list applies to every value. |
| Unknown parameters | [R4 search.html#errors](https://hl7.org/fhir/R4/search.html#errors) | Servers SHOULD ignore unknown or unsupported parameters by default and SHOULD honour `Prefer: handling=strict` by returning an error. The REST layer already handles this. Rejecting unsupported parameter types outright, as we do, is stricter than the default. |
| Paging | [R4 http.html#paging](https://hl7.org/fhir/R4/http.html#paging), [build](https://build.fhir.org/http.html#paging) | Page links are opaque and a `self` link is required; first, previous, next and last are "optional, but recommended" in R4. The build adds: SHOULD NOT include `previous` on the first page and SHOULD NOT include `next` when there are no more results. Both: never return more than `_count`, `_count=0` behaves as `_summary=count` (a total with no entries), `_total` is optional, and behaviour when data changes mid-paging is up to the server. Neither version defines cursor or offset paging. |

**Where R4 and the build differ on in-scope rules.** Paging best practices (no `previous` on page one, no `next` after the last page) exist only in the build, and we follow them because MongoDB does. The build rewrites the date prefix definitions as boundary tests with half-open examples; R4 uses range overlap with inclusive-end examples. Helios's shared `range_predicate` encodes R4's overlap semantics over half-open stored ranges, and we reuse it, so all backends agree. The build drops "escape" from URI sensitivity, adds `id` to the token table and to the no-pipe rule, weakens the 410-after-delete wording, downgrades ETag and Last-Modified on update from SHALL to SHOULD, and adds `:text-advanced`, `:code-text` and `:iterate` to the modifier table. None of these changes what the backend must store.

## Traits, structs and enums the backend must respect

Turning from the specification to the code, the server accepts a primary backend only if it implements 12 traits. Of these, only `ResourceStorage` and `SearchProvider` carry our scope, along with `VersionedStorage`, which the history traits and the vread handler require. The other ten we stub with explicit "unsupported" errors. `create_app` in `crates/rest/src/lib.rs` takes a generic `S: ResourceStorage + ConditionalStorage + SearchProvider + IncludeProvider + RevincludeProvider + InstanceHistoryProvider + TypeHistoryProvider + SystemHistoryProvider + BundleProvider + ExportDataProvider + PatientExportProvider + GroupExportProvider`; `create_app_with_config`, `create_app_with_auth` and `build_app` carry the same bound.

Paths below are relative to `crates/persistence/src` unless stated.

### Traits

| Trait (file) | Required methods | Cassandra |
| --- | --- | --- |
| `ResourceStorage` (`core/storage.rs`) | `backend_name`, `create`, `create_or_update`, `read`, `update(tenant, current, resource)`, `delete`, `count(tenant, Option<type>)` | Real. `update` is the compare-and-swap that If-Match relies on. `count` with `None` means all types. |
| `VersionedStorage` (`core/versioned.rs`) | `vread`, `update_with_match`, `delete_with_match`, `list_versions` | Real. A supertrait of `InstanceHistoryProvider` and required directly by the vread handler. `update_with_match` may return `OptimisticLockFailure` (412) or `VersionConflict` (409) per its doc; `delete_with_match` returns `VersionConflict`. REST does not call either for If-Match. |
| `SearchProvider` (`core/search.rs`) | `search`, `search_count`, `search_param_registry` | Real for token, date and URI. `search_param_registry` is called on every search, by capabilities, batch, compartment, `$everything`, bulk export and SQL-on-FHIR. |
| `SearchCapabilityProvider` (`core/capabilities.rs`) | `resource_search_capabilities`, `global_search_capabilities` | Real. Declares token, date and URI with no modifiers, plus `Count` and `Cursor` paging. Not in the server bound, and not consulted by the CapabilityStatement handler (see rejection section). |
| `Backend` (`core/backend.rs`) | `type Connection`, `kind`, `name`, `supports`, `capabilities`, `acquire`, `release`, `health_check`, `initialize`, `migrate` | Real. `kind()` returns `BackendKind::Cassandra`, which already exists as a reserved variant. Not in the server bound; required by the capability contract test. |
| `ConditionalStorage` (`core/storage.rs`) | `conditional_create`, `conditional_update`, `conditional_delete` | Stub. Override `supports_conditional` to `false`: the default claims support for create, update and delete. |
| `IncludeProvider`, `RevincludeProvider` (`core/search.rs`) | `resolve_includes`, `resolve_revincludes` | Compile-only stubs. REST resolves includes through `resolve_includes_iterative` over `SearchProvider`, never through these traits, so the real refusal lives in `search()`. |
| `InstanceHistoryProvider`, `TypeHistoryProvider`, `SystemHistoryProvider` (`core/history.rs`) | `history_*` and `history_*_count` | Stub |
| `BundleProvider` (`core/transaction.rs`) | `supports_atomic_transactions`, `supports_conditional_in_transaction`, `process_transaction_with_patch_validator` | Stub: `false`, `false`, `TransactionError::AtomicityUnsupported { backend_name }`, as S3 does. Batch never touches this trait. |
| `ExportDataProvider`, `PatientExportProvider`, `GroupExportProvider` (`core/bulk_export.rs`) | listing, counting and fetching for export | Stub, since bulk export is out of scope |

Every other stub returns `StorageError::Backend(BackendError::UnsupportedCapability { backend_name: "cassandra".into(), capability })`, which the REST layer maps to 501. That is "refuse explicitly" from #28, enforced by the compiler.

### Defaults we must override

Beyond the required methods, several provided defaults are wrong for a networked store, so we override them.

| Default | Problem | Override |
| --- | --- | --- |
| `ResourceStorage::readiness_check` returns `Ok` | `/_readiness` would report ready while Cassandra is down; the doc says networked backends MUST override | Delegate to `Backend::health_check` |
| `ResourceStorage::is_cluster_shared` returns `false` | Under-reports a networked store | Return `true` |
| `ResourceStorage::bulk_write_concurrency` returns 1 | Batch bundles and `create_many` run one entry at a time | Return 8, matching PostgreSQL and MongoDB. Batch further caps this at `HFS_BATCH_MAX_CONCURRENCY` (default 16) and forces 1 when any entry is conditional. |
| `ResourceStorage::delete_versioned` reads, then deletes | Not atomic, so an If-Match delete can race | Override with a lightweight transaction: `UPDATE resources SET deleted_at = ?, version_id = N+1 ... IF version_id = N AND deleted_at = null` (soft delete, never a CQL `DELETE`) |
| `ResourceStorage::create_many` loops over `create` | Startup seeds about 1,400 conformance resources per tenant through it (see startup section) | Keep the loop but run it at `bulk_write_concurrency`, as the default already does; measure boot time |
| `ResourceStorage::read_batch` reads sequentially | Include resolution and `_id` lists would issue N round trips | Fan out concurrent point reads |
| `ConditionalStorage::supports_conditional` returns `true` for create, update and delete | Advertises conditional operations we do not have | Return `false` |

### Structs and enums

The traits above exchange the following types, and each has a contract we must also respect.

| Type (file) | What we must respect |
| --- | --- |
| `TenantContext`, `TenantId` (`tenant/context.rs`, `tenant/id.rs`) | Every key starts with `tenant.tenant_id().as_str()`. Ids are case-sensitive, up to 64 bytes, ASCII letters, digits and `- _ . /`, with no empty segment, and must never be folded or truncated. `__system__` is reserved by `TenantId::parse` and comes from `TenantId::system()`; for us it is just another partition value. |
| `TenantContext::check_permission` (`tenant/context.rs`), `Operation` (`tenant/permissions.rs`) | Call `tenant.check_permission(Operation::…, resource_type)?` at the start of every write, as PostgreSQL and MongoDB do in create, update, delete and revive |
| `StoredResource` (`types/stored_resource.rs`) | Build rows with `StoredResource::from_storage(…)`. Versions are numeric strings ("1", "2", …) at this boundary and the ETag is always `W/"<version_id>"`. A deleted version has `deleted_at` set. We store `version_id` as a CQL `int` so that versions sort numerically. |
| `ResourceError` (`error.rs`) | `NotFound` maps to 404, `Gone` to 410 (`read` must return it for a deleted resource), and `AlreadyExists` to 409 |
| `ConcurrencyError` (`error.rs`) | `VersionConflict` maps to 409 and `OptimisticLockFailure` to 412 |
| `SearchError` (`error.rs`) | `UnsupportedModifier`, `UnsupportedParameterType`, `InvalidCursor`, `QueryParseError` and `InvalidDateValue` map to 400; `ChainedSearchNotSupported`, `ReverseChainNotSupported`, `IncludeNotSupported` and `TextSearchNotAvailable` map to 501 |
| `BackendError` (`error.rs`) | `Unavailable`, `ConnectionFailed` and `PoolExhausted` map to 503, `Timeout` to 504, and `UnsupportedCapability` to 501 |
| `BackendKind::Cassandra`, `BackendCapability` (`core/backend.rs`) | Declare `Crud`, `Versioning`, `OptimisticLocking`, `BasicSearch`, `DateSearch`, `CursorPagination` and exactly one placement capability, `SharedSchema`. There is no `TokenSearch` or `UriSearch` variant; `BasicSearch` covers token. The contract test in `tests/backend_capability_contract.rs` enforces one placement, but only for backends with a module there, so we add a Cassandra module with a golden capability list. |
| `SearchQuery`, `SearchParameter`, `SearchValue`, `SearchModifier`, `SearchPrefix` (`types/search_params.rs`) | The parsed query we receive. Multiple values are ORed, and multiple parameters are ANDed. |
| `PageCursor`, `CursorValue`, `PageInfo`, `Page<T>` (`types/pagination.rs`) | Reuse `PageCursor::new`/`encode`/`decode` as they are. A malformed cursor returns `SearchError::InvalidCursor`. Always mint a `next_cursor` when there is a next page: if a backend reports a next page without one, REST falls back to `_offset` links, which we refuse. |
| `SearchParamFullCapability`, `PaginationCapability` (`types/search_capabilities.rs`) | Declare token, date and URI with an empty modifier set, and paging as `Count`, `Cursor`, `MaxPageSize` and `DefaultPageSize` |
| `FhirVersion` (`crates/fhir/src/lib.rs`) | Stored on every resource and version row as `as_mime_param()`, read back with `from_storage`, defaulted with `default_enabled()`. Never hard-coded to `R4`. See the FHIR versions section. |

### Shared helpers we reuse instead of rewriting

- **Extraction:** `SearchParameterExtractor::extract` (`search/extractor.rs`) returns `ExtractedValue`s whose `IndexValue` (`search/converters.rs`) is `Token { system, code, display, … }`, `Date { value, precision, end }` or `Uri(String)`. PostgreSQL and MongoDB call it on every create and update and replace the old rows.
- **Dates:** `indexed_range(&IndexValue, StorageResolution::Millis)` (`search/date_value.rs`) gives each stored value a half-open `[start, end)`. `FhirDateValue::parse(raw)?.range_predicate(prefix, res)` turns a query into a `RangePredicate`. `validate_date_values(&query)` must run at the start of every search, next to `reject_unsupported_metadata_modifier` as its doc says.
- **Tokens:** follow MongoDB's split on `|` (`build_token_filter` in `backends/mongodb/search_impl.rs`). `IMPLICIT_TOKEN_SYSTEM` (`search/converters.rs`) marks `code`-typed elements. PostgreSQL, SQLite and MongoDB agree: `|code` matches system null, `''` or the marker; `sys|code` matches `sys` or the marker; `sys|` matches `sys` only; bare `code` matches any system. We do the same. **Decision: token matching is case-sensitive.** That is the spec default (case-insensitive matching is a SHOULD only when the code system's case rules are unknown) and it is what PostgreSQL and MongoDB do, so all backends agree.
- **Rejection:** nothing in the REST layer calls `SearchCapabilityProvider::validate_search_query`. MongoDB's `validate_query_support` refuses chains, `_has` and modifiers it cannot serve from inside `search()`; it never refuses a parameter type because MongoDB supports them all. Our `search()` refuses both, and also runs `validate_value_presence` and `reject_unsupported_metadata_modifier` as the other backends do.

## FHIR versions: R4 now, R4B, R5 and R6 without rework

We test against R4 only, but Helios is a multi-version server and the backend must not become the one R4-only component in it. The plumbing already exists, so the rule for us is simply to use it everywhere and hard-code nothing.

**What the code already provides.**

- `FhirVersion` (`crates/fhir/src/lib.rs`) has the variants `R4`, `R4B`, `R5` and `R6`, each behind a cargo feature of the same name. The persistence, rest and hfs crates default to `R4`; the book builds all four with `--features R4,R4B,R5,R6`. Helpers: `as_str()` gives `"R4"`, `as_mime_param()` gives `"4.0"`, `"4.3"`, `"5.0"` or `"6.0"`, `from_storage(&str)` accepts either form, `enabled_versions()` lists what this build has, and `default_enabled()` is the safe default (`FhirVersion::default()` is itself gated on the `R4` feature and does not compile in an R4B-only build).
- The version is decided per request, not per server. `create.rs` calls `storage_version_or(config.default_fhir_version)`, which takes the `fhirVersion` parameter of the request's `Content-Type` and falls back to `HFS_DEFAULT_FHIR_VERSION` (default `R4`). One server can therefore hold resources of several versions in one store, and `create`, `create_many` and `create_or_update` all receive the version as an argument.
- `StoredResource` carries `fhir_version`, and `from_storage(...)` requires it. PostgreSQL stores it in a `fhir_version` column written with `as_mime_param()` and read back with `from_storage`, falling back to `default_enabled()`; MongoDB stores the same string in a `fhir_version` field with the same fallback (`extract_fhir_version(doc, fallback)`).
- Each backend's config carries the server default as `fhir_version`, set from `server_config.default_fhir_version` in `main.rs`. The backends use it for `ResourceTypeScope::version(...)` (the resource-type name table that `:[type]` qualifiers and error messages are judged against), for the SQL-on-FHIR runner, and in PostgreSQL for one R4-only fast path guarded by `#[cfg(feature = "R4")]`.
- The spec data is already per version: `data/search-parameters-{r4,r4b,r5,r6}.json` and `compartment-definitions-*.json`. `SearchParameterLoader::new(fhir_version)` loads the right bundle, `seed_conformance_resources` seeds it per tenant, and `SearchParameterExtractor::new(registry)` is version-neutral because the registry it wraps was built from that loader.

**What the Cassandra backend does with it.**

- `resources` and `resource_versions` carry a `fhir_version text` column, written with `as_mime_param()` and parsed with `from_storage`, with `default_enabled()` as the fallback, exactly as PostgreSQL and MongoDB do. Tables and keys are shared across versions, as in every other backend; the version is a property of the row, not of the keyspace.
- Index tables do not need the version. Search loads the `resources` row for the tag check anyway and builds the `StoredResource` from it.
- No `FhirVersion::R4` literal appears outside tests. Defaults come from `default_enabled()` and `self.config().fhir_version`; version-specific behaviour, if any is ever needed, goes behind `#[cfg(feature = ...)]` the way PostgreSQL does it.
- The search-parameter registry is the one the server hands us through `TenantSearchRegistries`, so R4B, R5 and R6 parameter definitions arrive without backend changes.
- CI runs `cargo check -p helios-persistence --no-default-features --features cassandra,R4B` next to the R4 build, which is the cheapest proof that nothing in the backend assumes R4. **Decision:** functional tests stay on R4 fixtures for this project, and the R4B compile check is the gate. Running the shared suites under an R5 build is a follow-up once the R4 backend is accepted.

## Proposed Cassandra data model

We propose ten tables, nine of them led by `tenant_id`; the tenth is the internal outbox, explained below. Each table answers one access pattern, which is how Cassandra wants to be modelled. Leading with `tenant_id` follows #28's "`tenant_id` must be the leading column" rule, carried into partition keys.

**Decision: shared schema.** #28's early matrix suggested a keyspace per tenant for Cassandra. We use one keyspace and one set of tables with the tenant in every partition key, matching every other backend and the `SharedSchema` capability. A keyspace per tenant would multiply tables, prepared statements and repair work per tenant, and Helios's placement model has no counterpart for it. On types, `id` is `text` (bytewise order matches Rust string order; the `uuid` type sorts by version and time and would not), `version_id` is `int`, and `last_updated` is a CQL `timestamp`, which has millisecond precision.

| Table | Partition key | Clustering | Serves |
| --- | --- | --- | --- |
| `resources` | `(tenant_id, resource_type, id)` | — | `read`, `exists`, `_id`, and the compare-and-swap on `version_id` and `deleted_at` for every write. Also holds `fhir_version` and `write_ts`, the timestamp of the current version's index writes. |
| `resource_versions` | `(tenant_id, resource_type, id)` | `version_id DESC` | `vread`, `list_versions`, and delete markers (a version row with no content). Each row also carries its `fhir_version`. |
| `pending_index_writes` | `(bucket, shard)` | `tenant_id, enqueued_at, resource_type, id` | Intent rows for the index sweeper: written before every compare-and-swap, deleted after the index writes complete, `default_time_to_live` 24 h. `bucket` is the UTC hour, `shard` is `hash(tenant_id, id) mod 16`, and each row carries the request's `write_id`. |
| `resources_by_type` | `(tenant_id, resource_type)` | `last_updated DESC, id DESC` | A type search with no filters, `_lastUpdated`, `count`, and cursor paging in the default order |
| `token_code_index` | `(tenant_id, resource_type, param, code)` | `last_updated DESC, id DESC, system` | The bare `code` form (any system) |
| `token_system_code_index` | `(tenant_id, resource_type, param, system, code)` | `last_updated DESC, id DESC` | `system\|code` and `\|code` |
| `token_system_index` | `(tenant_id, resource_type, param, system)` | `last_updated DESC, id DESC, code` | `system\|` |
| `date_index` | `(tenant_id, resource_type, param)` | `start, id, end` | Date-only search for prefixes that bound the range start |
| `date_index_by_end` | `(tenant_id, resource_type, param)` | `end, id, start` | Date-only search for prefixes that bound the range end |
| `uri_index` | `(tenant_id, resource_type, param, uri)` | `last_updated DESC, id DESC` | Exact URI match |

The six index tables are rewritten on every create, update and delete from `SearchParameterExtractor::extract`. Every index row carries the resource's `version_id` as a regular column. `pending_index_writes` is not an index; it is the outbox that lets a background sweeper finish any write that crashed between the compare-and-swap and the index writes (see failure handling). It is the one table not led by `tenant_id`, deliberately: the sweeper has to find pending work without a tenant list, and this project has no tenant registry to enumerate from. Keying by hour bucket and a 16-way shard gives the sweeper 32 fixed partitions to poll and keeps any one of them small. Tenant isolation is not weakened, because the table holds keys and a `write_id`, never resource content, and only the sweeper reads it; `tenant_id` is still the first clustering column, so the rows it finds are applied under that tenant's context.

**Why these keys:**

- **Every token form reads one or two partitions, with no `ALLOW FILTERING`.** Filtering on a regular column needs `ALLOW FILTERING` and reads every non-matching row in the slice. So each form gets its own table, at the cost of writing each token value three times.
    - "No system" is stored as the sentinel `''`, because primary-key columns cannot be null. An empty string is valid as one component of a composite partition key.
    - `code`-typed elements are stored under `IMPLICIT_TOKEN_SYSTEM`. As a result, `sys|code` reads two partitions (`sys` and the marker) and merges two sorted streams, and `|code` reads `''` and the marker. This is exactly what PostgreSQL and MongoDB match.
- **Clustering keys keep distinct values apart.** `system` is in `token_code_index`'s clustering key, so two codings with the same code and different systems stay two rows. `end` is in `date_index`'s, so two ranges with the same start stay two rows.
- **The default order is `(last_updated DESC, id DESC)`.** That is MongoDB's default keyset. Sorting is ✗, so this one order is the only one we need. `last_updated` is truncated to milliseconds on write and in the cursor, matching `StorageResolution::Millis`; ties within a millisecond are broken by `id`.
- **The cursor is a plain `PageCursor`.** `sort_values = [last_updated as RFC 3339 with millisecond precision]` and `resource_id = id`, encoded with the existing `PageCursor::encode`.
- **A single-parameter token or URI search pages natively** with `WHERE … AND (last_updated, id) < (?, ?) LIMIT n`. Multi-column relations compare by value, so on our `DESC, DESC` order this is exactly the rows after the cursor, and it excludes every row of the cursor's own resource. Because `token_code_index` and `token_system_index` add a third clustering column, one resource can have several adjacent rows (two LOINC codes in one system, for example), and the two-partition merge for `sys|code` can yield one id from both streams. We therefore collapse rows on `(last_updated, id)` while streaming and keep reading until we have `_count + 1` distinct resources whose version tag matches the `resources` row. The extra one decides the `next` link. `LIMIT` counts rows, not resources, so it is a batch size, not the page size.
- **Multi-parameter searches stream in the shared order.** `resources_by_type` and every token and URI table share `(last_updated DESC, id DESC)`. One partition drives, ideally the most selective, starting at the cursor; each candidate is checked against the other token and URI parameters with a clustering point read (`WHERE <partition> AND last_updated = ? AND id = ?`), and we stop at `_count + 1` distinct matches. Commas within a parameter are a union of partitions merged in the same order. Nothing is materialized beyond one page.
- **Date predicates combined with any other parameter are residual filters.** We already load the `resources` row for the tag check, so we re-extract its dates and apply `RangePredicate::matches`. Only a date-only search touches the date tables.
- **Date-only searches slice whichever date table has the tighter bound, then check every row with `RangePredicate::matches`.** The slices follow Helios's `range_predicate`: `eq` bounds `start` on both sides; `lt`, `le` and `ap` give an upper bound on `start`; `sa` gives a lower bound on `start`. `gt` and `eb` are slices on `end` in `date_index_by_end`; `ge` is the union of an `end` slice and the `eq` slice; `ne` is the union of a `start` slice and an `end` slice. A date-only page cannot use the keyset order, so it is sorted in Rust and cut at the cursor, with a configured candidate cap (see rejection section). A range is allowed on only one clustering prefix per query, which is why the two date tables exist.
- **Index rows carry `version_id`.** Search checks that tag against the `resources` row it loads anyway, so a stale or orphaned index row never surfaces a resource or stale content. The tag check does not remove orphans; that is covered under failure handling.
- **Delete markers live in `resource_versions`.** A deleted resource keeps its `resources` row with `deleted_at` set, so `read` can return `ResourceError::Gone` (410). A later `create_or_update` brings it back. We say "delete marker", not tombstone, because Cassandra tombstones are a different thing that this design has to manage separately.

Replication is set on the keyspace, which uses `NetworkTopologyStrategy`, with replication factor 3 on the three-node cluster and 1 on a single local node. `LOCAL_SERIAL` is linearizable only within one data centre, which matches our deployment; a multi-DC deployment would need `SERIAL`.

**Decision: measure partition growth first, bucket on a trigger.** At 100,000 resources our largest partitions (`resources_by_type`, the two date tables, hot token values such as `status=final`) are about 5 to 15 MB, well under the 2-billion-cell limit and 4.1's 100 MiB large-partition warning (5.0 replaces that setting with a guardrail that is off by default). The real costs are different: each such partition is a hot spot served by one replica set, full-partition reads (`count`, the `end`-side date slices) cost O(rows), and every update leaves a row tombstone per index row. We keep single partitions for this project and add a time bucket to a partition key only when a measured trigger fires: tombstones scanned per read above 1,000 (the warn threshold), or a `count` or date scan above the p95 budget. So that bucketing can be added without breaking clients, the cursor's `sort_values` reserves a third slot for the bucket from day one, and the page walker is written to iterate buckets newest first.

## Consistency, failure handling and rejection

The data model splits a resource across several tables, so the resource row and its index rows need different guarantees. Every write to a `resources` row goes through a lightweight transaction (LWT), including revive. Index tables are never written with an LWT.

- **The REST layer checks `If-Match` itself** for single PUT, PATCH and DELETE. It returns 412 on a mismatch, then calls `ResourceStorage::update(tenant, current, resource)` or `delete_versioned`, and relies on that call as the compare-and-swap.
- **Losing the race is a 409.** A writer that changed the row after the REST layer's read must get `ConcurrencyError::VersionConflict`. A row soft-deleted in that gap must make the swap miss (404). `tests/search/versioned_write_race_suite.rs` states this contract.
- **Batch is different.** A batch PUT with `ifMatch` checks the version, then calls `create_or_update`, not `update`. Our `create_or_update` therefore reads the current row and runs the same compare-and-swap on the version it saw, retrying a bounded number of times on a miss, so two concurrent batch PUTs still get distinct versions.
- **Why every write.** Without an LWT on every write, two concurrent unconditional PUTs would both write version N+1. The cost is a Paxos round on every write, which our benchmarks will show next to PostgreSQL.

**Consistency levels.** Every statement sets its consistency explicitly; `cdrs-tokio` defaults to `ONE` and leaves serial consistency unset. Reads, plain writes and the commit phase of each LWT use `LOCAL_QUORUM`; the Paxos phase uses `serial_consistency = LOCAL_SERIAL`. A `LOCAL_QUORUM` read after an acknowledged LWT therefore sees it. We run `paxos_variant: v2` (two round trips per write; v1, the default in the 4.1 and 5.0 `cassandra.yaml`, needs four) and say so in every benchmark report.

**Decision: driver.** We stay on `cdrs-tokio` 8 as the crate already declares it (locked 8.1.9; 9.0.x shipped in 2026 and supports protocol v3 to v5). It is essentially a single-maintainer project, and the two advisories `audit.toml` ignores for it (`derivative` and `fxhash`, both "unmaintained") remain in 9.0.2, but staying on it changes no maintainer-owned file and it exposes everything this design needs: per-statement serial consistency, typed write-timeout errors with `write_type`, prepared statements and manual paging. The `scylla` driver (1.9, monthly releases, CI against a three-node Apache Cassandra cluster, protocol v4 only) is the named fallback if a blocking bug appears; because it speaks v4, an unknown CAS outcome would then arrive as `WriteTimeout` with `write_type = CAS` rather than `CAS_WRITE_UNKNOWN`, which the timeout handling below already covers.

**Write path (update shown):**

1. Check `tenant.check_permission(Operation::Update, type)`. Extract the index rows for the new content, and re-extract the old ones from `current`.
2. Write the intent row: `INSERT INTO pending_index_writes (bucket, shard, tenant_id, enqueued_at, resource_type, id, write_id)` at `LOCAL_QUORUM`, with the `write_id` this request will use in its compare-and-swap. This is a plain write, not an LWT. If it fails, return 503 and nothing has changed.
3. Run the compare-and-swap. If it is not applied, return `VersionConflict`; nothing else has been written. Cassandra returns the current values of the condition columns when a CAS is not applied, so 404, 409 and 410 are chosen without a second read. The CAS also sets `write_ts(N+1) = max(now_µs, write_ts(N) + 1)` and a per-request `write_id`.
    - **Update:** `UPDATE resources SET …, version_id = N+1, write_ts = ?, write_id = ? IF version_id = N AND deleted_at = null`.
    - **Create:** `INSERT … IF NOT EXISTS`. Do not use a CAS whose only conditions are null checks: on a missing row those are true and would create a ghost row.
    - **Delete and `delete_versioned`:** `UPDATE … SET deleted_at = ?, version_id = N+1 IF version_id = N AND deleted_at = null`. Do not use a CQL `DELETE`, which would erase the row and break 410.
    - **Revive:** `create_or_update` drops the `deleted_at` condition but keeps `IF version_id = N`.
4. Write the `resource_versions` row for N+1 as its own statement, `USING TIMESTAMP write_ts(N+1)`. Resource content never goes into a multi-partition batch.
5. Write the index changes, all `USING TIMESTAMP write_ts(N+1)`: delete the index and `resources_by_type` rows whose keys are no longer produced, and upsert the rows that are. A key present in both the old and new sets is upserted only. Because `last_updated` is part of most clustering keys, almost every key changes on every update, so this is one delete and one insert per index row. We group them into logged batches kept under `batch_size_warn_threshold` (5 KiB; the fail threshold is 50 KiB and applies to any multi-partition batch) and send the batches concurrently.
6. Once every batch is acknowledged, delete the intent row and return success. On a batch failure, retry with the same timestamps. A `WriteTimeout` of type `BATCH` needs no retry, because the batchlog guarantees replay; `BATCH_LOG` means the batchlog write itself failed, so retry. If the intent-row delete fails, return success anyway: the sweeper will find the index already current and delete it.

**Why the fixed timestamp matters.** Two concurrent updates N+1 and N+2 are ordered by the LWT, but their index writes race. Without a fixed timestamp, each batch would get the coordinator's clock and last-write-wins would let a late N+1 batch resurrect rows N+2 deleted, or overwrite tag N+2 with N+1 in a table whose key did not change. With `write_ts` strictly increasing per version, a delete at `write_ts(N+2)` beats an insert at `write_ts(N+1)` whatever order they arrive in, and a retry is genuinely idempotent. Separately, do not bind `null` for absent columns; leave them unset, or every write adds cell tombstones.

**When the LWT outcome is unknown.** A `WriteTimeout` with `write_type = CAS` (or protocol v5's `CAS_WRITE_UNKNOWN`) leaves the outcome open. We read the row back at `LOCAL_SERIAL`, which completes or permanently cancels the in-flight proposal, and compare `write_id`. If it is ours, the write succeeded and we continue at step 4. If the serial read also times out we return 503 rather than retrying and reporting a false 409 against our own success. A `WriteTimeout` with `write_type = SIMPLE` means the CAS was decided and only the commit timed out, so the write is applied. If another writer has already reached N+2, the `write_id` check reports a false 503 for our request; we accept that.

**The failure window.** In Cassandra 4.x and 5.0 an LWT is limited to one partition, and a logged batch is atomic (eventually all or nothing) but isolated only within a single partition. Multi-partition ACID transactions (Accord, CEP-15) are targeted at 6.0, which is not generally available, and we do not depend on them. So step 3 and steps 4 to 6 cannot be one operation, and nothing in Cassandra replays steps 4 to 6 if the Helios process dies between them.

- **During every update, briefly.** Between the CAS and the index writes, the resource is hidden from search: its old index rows fail the tag check and its new rows are not yet written. PostgreSQL would return one version or the other. We state this as intended behaviour.
- **What a crash between them leaves.** The resource row is correct and `read` and `vread` are right, but its index rows carry tag N, so the tag check hides the resource from search. Search never returns wrong content. The N rows are never cleaned by a later update either, because the update to N+2 deletes the keys computed from N+1, which were never written.
- **Decision: an intent row and a sweeper close the window.** This is the dual-write problem, and the documented Cassandra pattern for it is the transactional outbox: record the intent in a table Cassandra can write cheaply, do the work, and let a poller finish anything left behind. Step 2 writes that intent row before the compare-and-swap, step 6 deletes it afterwards, and a background task in the backend polls the 16 shards of the current and previous hour bucket of `pending_index_writes` every few seconds (configurable). For each row older than a short grace period (30 s by default, so in-flight requests are left alone), the sweeper reads the `resources` row at `LOCAL_SERIAL`, which also settles any in-flight Paxos proposal, and compares `write_id`. If the resource's `write_id` equals the intent's, the compare-and-swap applied and the index writes may not have: the sweeper re-runs steps 4 and 5 for that version with its stored `write_ts` and `write_id`, taking the previous version's keys from its `resource_versions` row since no `current` is in hand, then deletes the intent row. If the `write_id` differs or the row does not exist, this request's compare-and-swap never applied (or a later version has already superseded it, whose own intent row covers it), and the intent row is simply deleted. No clocks are compared. Every step is idempotent because the timestamps are fixed, so a sweeper and a slow request can both run the same writes without harm. The intent rows have a 24-hour TTL, so a sweeper outage cannot grow the table without bound; the tag check still guarantees that nothing wrong is ever returned in the meantime.
- **Repair on read stays as the second line of defence.** When search finds an index row whose tag disagrees with the `resources` row, it re-runs the index maintenance for the current version inline and deletes the stale key it found. This heals orphans the sweeper could not know about, such as rows left by a crash older than the TTL.
- **Alternatives we considered.** Cassandra 5.0's Storage-Attached Indexes remove the dual write entirely ("when a write is acknowledged to the client, the data is already indexed"), but a query without a partition key scans the token ring, there is no `ORDER BY` on non-vector columns so keyset paging by `last_updated` is lost, and the default cap is 10 indexes per table against hundreds of FHIR search parameters. Materialized views have been experimental and disabled by default since 3.0.15 and have no reconciliation mechanism. Change data capture would move index maintenance out of process, which is the right shape for a later Elasticsearch composite but not for the primary store's own search tables. Accord (CEP-15) would make the whole write one transaction, but it is not generally available.
- **How we test it.** The controlled failure tests in the proposal kill the Helios process at two points. Killed between the intent row and the compare-and-swap, the sweeper must delete the intent and change nothing else. Killed between the compare-and-swap and the index writes, `read` and `vread` must be correct immediately, search must hide the resource until the sweeper runs, and then return it; `count` is checked before and after.

**Tombstones.** Because `last_updated` is in the clustering keys, every update leaves one row tombstone per old index row, and the `resources_by_type` row moves to the head of its partition leaving a tombstone behind. `count` and the date scans read through them. The defaults are `tombstone_warn_threshold: 1000` and `tombstone_failure_threshold: 100000` per query. Tombstones stay until `gc_grace_seconds` (10 days) passes and, with replication factor 3, repair has run on every node. A node offline longer than that must not rejoin without repair. The tag check makes a resurrected index row harmless, so `gc_grace_seconds` can be lowered on the index tables alone. We reset data between benchmark runs and record tombstones scanned per read.

**Search visibility.** Step 6 returns only after the index writes are acknowledged, so any write the client saw succeed is searchable, and `read` and `vread` at `LOCAL_QUORUM` see it immediately.

A related default also needs justification. The default no-op `ensure_writes_visible` is documented as valid only when the index is written in the same transaction as the resource, which is not true here. Its callers are conditional references and `If-None-Exist`, both out of scope and unreachable once `supports_atomic_transactions` is false. We keep the no-op and document why it still holds.

**Capabilities and rejection.** Rejection is split between REST and the backend, and we need to be clear about which does what:

- The REST layer already validates modifiers against parameter types for every registered parameter (`validate_modifier` in `search/value_parser.rs`, called from `extractors/search_query_builder.rs`), so `:exact` on a token, date or URI parameter is a 400 before `search()` runs. It also handles unknown parameters and `Prefer: handling=strict`.
- The REST layer rewrites chains, `_has` and `_list` into `_id` filters by running per-hop searches first (`resolve_chains_with`). A chain on a Cassandra primary therefore fails at the hop that needs a reference parameter, as 400 `UnsupportedParameterType`, not as 501 from `ChainedSearchNotSupported`. The `_id` filter itself must work, which is why `_id` is in scope.
- Inside `search()` and `search_count()` we run `validate_date_values`, `validate_value_presence` and `reject_unsupported_metadata_modifier` first; refuse any parameter type other than token, date and URI with `UnsupportedParameterType` (400); refuse any modifier with `UnsupportedModifier` (400), which keeps the backend correct when it is called directly rather than through REST; refuse `_include` and `_revinclude` when `query.includes` is non-empty with `IncludeNotSupported` (501), which works because `search()` runs before include resolution; refuse `_text` and `_content` with `TextSearchNotAvailable` (501); and refuse `_offset` and any `_sort` other than the default with `QueryParseError` (400). MongoDB uses that error for a cursor on a sort it cannot key; unlike MongoDB we do not honour `_offset` at all.
- A date-only or otherwise unbounded search whose candidate set exceeds a configured limit returns an OperationOutcome with issue type `too-costly` instead of timing out.
- `SearchCapabilityProvider` and `BackendCapability` describe the same surface, and the README matrix will be updated to match. The CapabilityStatement handler (`crates/rest/src/handlers/capabilities.rs`) does not read either: it lists every registered search parameter of every type and hard-codes `vread`, the three history interactions, `versioning: versioned` and `readHistory: true`. A Cassandra deployment would therefore over-advertise, and a client that trusts the statement would discover string or reference search and history as 400s and 501s at run time. **Decision: we patch the handler as part of this project.** The patch follows the pattern the handler already uses for `supports_conditional`, `supports_contained_search` and `modifiers_for_param_type`: defaulted hooks on traits already in the server bound, so no existing backend changes.
    - `SearchProvider::supported_param_types()` returns every `SearchParamType` by default; Cassandra returns token, date and URI. `build_search_params` drops parameters of other types, and `build_resource_capability` drops `_include`/`_revinclude` entries when the backend returns `None` from the include hooks.
    - `InstanceHistoryProvider::supports_history()` returns `true` by default; Cassandra returns `false`. The handler then omits `history-instance`, `history-type` and `history-system` and sets `readHistory: false`, while keeping `vread` and `versioning: versioned`, which we do support. `build_capability_statement` adds `InstanceHistoryProvider` to its own bound, which costs nothing because `create_app` already requires it.
    - We do not put `SearchCapabilityProvider` in the server bound: S3 does not implement it, so that route would break an existing backend. The two hooks delegate to the same `SearchCapabilityProvider` data inside the Cassandra backend, so there is one source of truth.
    - Tests: the existing `crates/rest/tests/capabilities_search_params.rs` and `rest_conformance.rs` gain a stub backend that overrides both hooks and asserts the statement omits what the backend refuses; the default-path tests stay green for the other backends.
    - The patch goes upstream as its own pull request, separate from the backend, because it fixes the same over-reporting for any backend that refuses what the handler hard-codes.

## What else the server expects from a primary backend

Beyond the matrix and the traits, the server expects several further things from a primary backend. The items below are not in the matrix; they surfaced while reading `crates/hfs/src/main.rs` and the other `start_*` functions.

- **Backend selection.** `HFS_STORAGE_BACKEND` is parsed into `StorageBackendMode` in `crates/rest/src/config.rs`, which needs a Cassandra variant with `Display`, `FromStr` and `primary_backend_kind`. `main.rs` dispatches to feature-gated `start_*` functions with `#[cfg(not(feature))]` fallbacks, and an exhaustive match for `patient_name_search_support` needs a Cassandra arm (`IdOnly`, like S3). The `cassandra` cargo feature exists only in the persistence crate today; `crates/rest/Cargo.toml` and `crates/hfs/Cargo.toml` must thread it through as they do for `mongodb`.
- **Conformance seeding at startup.** `seed_conformance_resources` writes about 1,400 SearchParameter and CompartmentDefinition resources per provisioned tenant through `create_many`. With an LWT on every write that is about 1,400 Paxos rounds per tenant at boot, fanned out at `bulk_write_concurrency`. We will measure it.
- **Search parameter registry.** Backends own a `TenantSearchRegistries` (`search/tenant_registries.rs`) and refresh stored SearchParameters periodically, as `spawn_mongodb_search_param_refresh` does. Cassandra needs the same to implement `search_param_registry`.
- **The `start_cassandra` arm**, modelled on `start_s3`, must decide `SessionPersistence` (or warn that login sessions are in-process), `SettingsStore` (501 if `None`), `BulkProviderStore`, `OperationsBundle` (`PurgableStorage` for `$purge`, `ReindexableStorage` for `$reindex`, or `None` for 501), `WriteObservability`, and export and submit bundles (`None`). Our first version passes `None` wherever S3 does.
- **Database audit.** `HFS_AUDIT_BACKEND=database` fails at startup for a Cassandra primary, which is consistent with "Cassandra never stores AuditEvents" but should be documented.
- **`_count=0` and `count`.** `_count=0` must behave as `_summary=count` in both spec versions, so it needs a total. Our `count` is a full scan of the `resources_by_type` partition and reads through its tombstones; it is a stated cost and a benchmark case.
- **Tenant registry.** The admin tenant API returns 501 unless `supports_tenant_registry` is true, and the tenant extractor skips the provisioned-tenant check when a backend has no registry, as it does for Elasticsearch today. **Decision:** no registry in this project. `supports_tenant_registry` stays `false`, tenants are whatever the request's tenant context names, and `register_tenant`, `deregister_tenant` and `purge_tenant_data` keep their default unsupported behaviour. A registry table is a natural follow-up and needs no schema change elsewhere.
- **Conformance testing with Inferno.** The fork inherits a complete Inferno pipeline (`.github/disabled-workflows/inferno-us-core.yml`, `crates/hfs/tests/inferno/install.sh` and fixtures) that runs the ONC US Core server suites v3.1.1 to v8.0.0 against every backend. Upstream treats it as a weekly tracking signal rather than a gate, and it needs self-hosted runners this fork does not have. US Core is also the wrong yardstick for a standalone Cassandra primary: its tests search by `patient` reference and by `name`, and add `_revinclude=Provenance:target`, so against our scope almost every group fails or skips by construction, as it does for standalone MongoDB upstream. **Decision:** we write a small Inferno test kit of our own, from `inferno-template`, whose tests are derived line by line from the rejection table above: a capability-truth group that checks `/metadata` advertises exactly what we support, CRUD and versioning, supported search with keyset paging, and a declared-rejection group where each unsupported request must return its documented status with an OperationOutcome. The kit needs no profile validation, so it runs without the validator service. We run it against PostgreSQL once as a check on the kit itself, and we run US Core v3.1.1 once against Cassandra as a documented negative result with every failure mapped to a rejection. A green US Core run needs the Cassandra + Elasticsearch composite and is future work.
- **Composite role.** The README lists a planned "Cassandra + Elasticsearch" composite. **Decision:** standalone primary only in this project. Nothing here blocks the composite later: the composite layer feeds its search backend from the primary's write path, and our index tables are internal to the primary, so a composite would simply route search elsewhere and leave them unused.

## Implementation order

The ordered plan, with milestones, exit criteria, test gates, failure tests, the measure-first triggers, file ownership and an indicative schedule, lives in [`development-roadmap.md`](development-roadmap.md). In one paragraph: the trait hierarchy sets the order, so the whole team designs the schema first, one owner wires the skeleton and stubs to a create/read round trip through REST (milestone A), CRUD and versioning follow, then the index writes and sweeper, then the search framework, after which token, date, URI, cursor paging and the CapabilityStatement hooks proceed in parallel in their own files, and benchmarks, failure tests and the demonstration close it out (milestones B and C). The benchmark harness, Docker files, CI and the PostgreSQL baseline start on day one because they need no Cassandra code.
