# ADR-aacruzgon-0018: CI runs on the team's self-hosted runner

- **Date:** 2026-10-14 (decided 2026-10-13, recorded 2026-10-14)
- **Status:** accepted
- **Context:**
    - **The roadmap disagreed with itself.** Section 1 ("Machines") said the 32 GB Apple-silicon laptop also runs the CI workflow; Step 0 said CI runs "on the GitHub-hosted workflow".
    - **Neither is the plan.** On 2026-10-13 Alan decided that the CI items in Step 0 (progress matrix 0.4 R4B compile check, 0.5 fmt, clippy and the Cassandra test job, 0.11 upstream canary) wait for a self-hosted GitHub Actions runner the team is setting up, and run there.
    - **No runner is registered yet.** `gh api repos/aacruzgon/hfs-Cassandra-CS4411/actions/runners` returned 0 runners on 2026-10-14.
    - **The inherited `ci.yml` is the precedent.** Every job in it targets `self-hosted` labels; it was archived to `.github/disabled-workflows/` because this fork had no such runner and its jobs queued forever.
- **Decision:**
    - Every workflow added for Step 0 (0.4, 0.5, 0.11) runs on the team's self-hosted runner, a machine with 32 GB of RAM and an AMD 7900X CPU. *Corrected 2026-10-14:* this first said "the team's own server, separate from the five team machines". The machine is Sam's own desktop, which he also develops on, registered as `sam-7900x` (ADR-sam-michaels-0001).
    - Its `runs-on` labels and OS are recorded in the roadmap Step 0 bullet when the runner is registered, and no CI workflow is written before then.
    - The CI items are built in this order: register the runner, then 0.4, then 0.5 (fmt, clippy, Cassandra job), then 0.11. Roadmap Step 0 lists the reasons.
- **Alternatives considered:**
    - **GitHub-hosted runners** (what Step 0 said): lost. The team wants CI on a machine it owns and controls, and its server (32 GB, AMD 7900X) has more memory and cores than a standard hosted runner for the `--all-features` clippy build.
    - **The 32 GB team laptop** (what section 1 said): lost. It may be the 32 GB machine that runs the report's benchmarks (roadmap section 1), which CI load would disturb, and a laptop that sleeps or leaves the network stalls every pull request.
- **Consequences:**
    - **Roadmap items 0.4, 0.5 and 0.11 are blocked until the runner is registered.** The week 1 schedule row (13 to 18 Oct) now says so. Step 2 (Milestone A, Wed 21 Oct 2026) can start without them, but its pull requests merge without the R4B check until 0.4 exists.
    - **The repository is public, so only collaborators' code runs on the runner.** GitHub warns against self-hosted runners on public repositories ("Forks of your public repository can potentially run dangerous code on your self-hosted runner by creating a pull request", shown on the Add runner page). A `pull_request` from a fork runs the workflow files *from the fork's branch*, so its author can write any `runs-on` and any steps, whatever our own workflows say. The only thing that stops it is approval. The rules:
        - **Repository setting (applied 2026-10-14):** fork pull request workflows need approval from every outside contributor, not only first-time ones (`approval_policy: all_external_contributors`; it was `first_time_contributors`). Nothing from a fork runs until someone with write access clicks "Approve and run".
        - **Nobody approves a fork pull request's workflows.** Approving one runs code the fork's author chose, on the team's server. The five collaborators push branches to this repository rather than to forks, so their own pull requests never need approval.
        - **Every job on the runner skips fork pull requests:** `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository`. This only stops our own, unmodified workflows from running a fork's code if one is approved by mistake. It does not stop an attacker, who can delete the guard in their pull request.
        - **No workflow uses `pull_request_target` or `workflow_run`.** Both run in the base repository's context even when a fork triggered them, so a step that checks out or downloads the fork's code would run it on the runner with the base repository's permissions.
    - **The residual risk is a mistaken approval.** GitHub has no setting that turns fork pull request workflows off on a public repository. Making the repository private removes the risk: it needs leaving the fork network first, because a fork of a public repository cannot be private; that is a separate decision.
    - **The runner itself holds nothing worth stealing.** It runs as a dedicated non-admin user, has no secrets beyond what the jobs need, and every workflow keeps the repository default of read-only `GITHUB_TOKEN`, except the canary (0.11), which needs `issues: write`.
    - **The Cassandra job needs Docker and at least 3 GiB free for the container** (`docker/cassandra`, ADR-aacruzgon-0002), plus room for the build output. *Corrected 2026-10-14:* this first said "the `rust-cache` cache"; CI keeps a bounded target directory on the runner instead (ADR-sam-michaels-0002).
    - **Out of scope:** `.github/workflows/coverage.yml` stays on GitHub-hosted `ubuntu-24.04`. The Inferno workflows in roadmap Step 8 still say "GitHub-hosted"; they are decided in Step 8.
- **AI involvement:**
    - **Tools:** Claude Code (Opus 5.5).
    - **What the AI proposed:** the order of the CI items and the reasons for it; recording the decision as an ADR and correcting the two roadmap statements; the public-repository safeguards (the approval setting, the job guard, no `pull_request_target` or `workflow_run`). The AI first wrote that the job guard skips fork pull requests even when approved; that was wrong, because a fork's pull request runs its own copy of the workflow files, and it was corrected before PR #15 merged.
    - **What the human changed:** Alan made the self-hosted decision on 2026-10-13 and gave the reason GitHub-hosted runners lost (the team wants its own machine) and the server's specification (32 GB, AMD 7900X), and asked for these fixes before handing the CI items to a teammate. Alan asked that only approved collaborators can run workflows and nobody who forks the repository can, and then asked whether anyone who forks the repository can run the workflows, which exposed the wrong claim about the guard.
    - **Verified:**
        - The runner count, with `gh api .../actions/runners` (0 on 2026-10-14).
        - The repository visibility, with `gh repo view` (public).
        - The approval setting, with `gh api .../actions/permissions/fork-pr-contributor-approval`: `first_time_contributors` before, `all_external_contributors` after the change on 2026-10-14. The default `GITHUB_TOKEN` is read-only (`.../actions/permissions/workflow`).
        - The `self-hosted` labels in `.github/disabled-workflows/ci.yml` and the archive reason in `.github/disabled-workflows/README.md`.
