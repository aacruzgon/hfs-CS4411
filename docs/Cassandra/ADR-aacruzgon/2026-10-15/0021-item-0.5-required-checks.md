# ADR-aacruzgon-0021: Item 0.5's four checks are required on `main`, the Cassandra schema job included

- **Date:** 2026-10-15
- **Status:** accepted
- **Context:**
    - ADR-aacruzgon-0019 made `cargo check (cassandra, R4B)` a required check on `main` and said fmt and clippy would join it when item 0.5 added them.
    - Item 0.5 merged on 2026-10-15 in PR #20 (merge commit `1c5421a32`), as `.github/workflows/fmt-clippy-cassandra.yml` with four jobs (ADR-sam-michaels-0003): `cargo fmt --check`, `cargo clippy (helios-fhir)`, `cargo clippy (workspace)` and `Cassandra schema (single node)`.
    - **ADR-0019 did not cover the Cassandra job.** It starts the single-node container on the runner, applies `schema/keyspace-single-node.cql` and `schema/schema.cql`, and checks that a second apply prints nothing and that keyspace `helios` has ten tables. From Step 2 it also runs the Cassandra test binary against that node (ADR-aacruzgon-0020).
    - **`cargo clippy (workspace)` has `needs: clippy-fhir`.** When `cargo clippy (helios-fhir)` fails, GitHub skips the workspace job, and a skipped job counts as passing.
- **Decision:**
    - **All four of item 0.5's jobs are required checks on `main`,** added on 2026-10-15 to the ruleset "Require PRs for main and master", each tied to the GitHub Actions app as in ADR-aacruzgon-0019. With the R4B check, `main` now requires five checks:
        - `cargo check (cassandra, R4B)`;
        - `cargo fmt --check`;
        - `cargo clippy (helios-fhir)`;
        - `cargo clippy (workspace)`;
        - `Cassandra schema (single node)`.
    - **Both clippy jobs are required,** so a failure in `cargo clippy (helios-fhir)` blocks the merge even though the workspace job is then skipped.
    - **The Cassandra job is required too,** beyond what ADR-0019 planned.
- **Alternatives considered:**
    - **Only fmt and clippy, as ADR-0019 planned:** lost. A pull request that breaks `schema.cql`, or makes a statement stop being idempotent, could merge with a red Cassandra job. The Step 1 design sessions are about to change that file, and from Step 2 this job is also where the Cassandra tests run.
    - **Require the Cassandra job only once Step 2 adds the test binary:** lost. The schema changes it checks happen in Step 1, before any test exists.
    - **Only `cargo clippy (workspace)`, relying on `needs:`:** lost. A skipped job counts as passing, so a failing `helios-fhir` lint would not block the merge.
- **Consequences:**
    - **Every pull request waits for the whole workflow:** about 10 s for fmt, about 70 s for the Cassandra job (most of it Cassandra's start-up), and seconds for clippy when `target/clippy` is warm, or about 8.7 minutes when it is cold (ADR-sam-michaels-0003, run 38672131127). The jobs run one after another on the single runner.
    - **A Cassandra job that fails for a reason unrelated to the change now blocks the merge.** ADR-sam-michaels-0003 records one known case: a host `cqlsh` timeout while the desktop is under heavy load. The fix is re-running the failed job, not an admin bypass.
    - **The job names are a contract.** Renaming a job's `name:` in `fmt-clippy-cassandra.yml` breaks the ruleset until the required check is renamed in the same change, as ADR-0019 says for the R4B check.
    - **These workflows must keep running on every pull request.** A `paths:` filter, or anything else that skips a whole workflow, would leave its required checks "Expected — Waiting for status" and block the pull request, the same failure as `[skip ci]`. Neither workflow has one today.
    - **The required checks do not make CI run on a fork's pull request.** Every job in both workflows carries the fork guard (ADR-aacruzgon-0018), and GitHub reports a job skipped by its `if:` as "Success", which satisfies a required check. So:
        - until someone clicks "Approve and run", nothing runs and all five checks stay "Expected — Waiting for status", which blocks the merge;
        - if someone approves by mistake, every job is skipped, all five checks show as passed without anything having been checked, and only the required approving review stands between that pull request and `main`.

      There is no fork-safe way to run these jobs: running them would run the fork's code on the runner, which ADR-0018 forbids. A fork's pull request is therefore never approved to run (ADR-0018), and its diff is reviewed as unchecked code.
    - **The runner must be on for any pull request to merge,** as ADR-0019 already says; this adds no new dependency on it.
- **AI involvement:**

    - **What the human changed:** Alan decided to require the Cassandra job as well, after PR #20 merged.
    - **Verified:**
        - The check names and their app (`github-actions`, id 15368), from the check runs on `main` at `1c5421a32`, all four green.
        - The ruleset before and after, with `gh api repos/aacruzgon/hfs-Cassandra-CS4411/rulesets/24684567`: the required list went from one check to five, and a diff showed every other rule, the bypass actors, the conditions and the enforcement unchanged.
